## 1단계 Git은 무엇을 기록하나

이 단계를 마치면 커밋 하나에 무엇이 담기는지, 그리고 무엇을 담으면 안 되는지 설명할 수 있습니다.

<DeepDive title="커밋 하나에 담기는 것">

커밋은 파일 복사본이 아니라 **바뀐 부분 + 누가 + 언제 + 왜**를 묶은 기록입니다.

| 담기는 것 | 예 | 학급 일지에 빗대면 |
| --- | --- | --- |
| 바뀐 내용 | `index.html` 3줄 수정 | 오늘 있었던 일 |
| 메시지 | "글자 수 계산기: 지우기 전에 한 번 묻기" | 한 줄 기록 |
| 작성자·시각 | 김가온, 2026-11-24 16:05 | 기록자와 날짜 |
| 바로 앞 커밋 | 직전 세이브 포인트 | 어제 쪽 |

그래서 파일 이름에 `_최종_v3`를 붙일 필요가 없습니다. 파일은 하나로 두고 이력은 Git이 맡습니다. 얼마나 자주 커밋할지는 <b>"잘 돌아갈 때마다, 기능 하나마다"</b>가 기준입니다. 하루 일을 커밋 하나에 몰면 되돌릴 때 잘된 부분까지 함께 사라지고, 글자 하나마다 커밋하면 이력이 길어 찾기 어렵습니다.

</DeepDive>

<DeepDive title="한 번 올라간 것은 지워도 남는다">

Git은 지난 기록을 버리지 않습니다. 되돌릴 수 있는 이유이자, 조심해야 하는 이유입니다. 비밀번호나 API 키가 든 파일을 한 번 커밋해 GitHub에 올리면, 다음 커밋에서 그 파일을 지워도 **이전 커밋에는 그대로 남아** 저장소를 볼 수 있는 사람은 꺼내 볼 수 있습니다.

- 키가 올라갔다면: 저장소에서 빼는 것과 별개로 **키를 새로 발급**받아 예전 키를 못 쓰게 만듭니다. 4회차부터 `.env.local`이라는 키 파일이 실제로 생깁니다.
- 학생 자료가 올라갔다면: 혼자 수습하지 말고 학교의 개인정보 담당자에게 바로 알립니다. 애초에 실습 폴더에 실제 학생 자료를 두지 않는 것이 가장 확실합니다.
- 예방: 첫 커밋 전에 `.gitignore`를 만들고, 푸시 전에 한 번 점검합니다.

</DeepDive>

## 2단계 커밋을 쌓고 되돌려 보기

이 단계를 마치면 상황에 맞는 되돌리기 방법을 고를 수 있습니다.

<DeepDive title="되돌리는 세 가지 방법">

| 상황 | 방법 | 어떻게 |
| --- | --- | --- |
| 방금 대화에서 시킨 일이 마음에 안 든다 | Claude Code의 되돌리기 | 입력창에 `/rewind` → 돌아갈 지점을 고르고 코드를 되돌리는 항목 선택 |
| 며칠 전 잘되던 상태로, 또는 파일 하나만 | 커밋으로 돌아가기 | "방금 커밋한 변경을 되돌려 줘", "README.md만 마지막 커밋 상태로" |
| 되돌리지는 않고 예전에 어땠는지만 보고 싶다 | GitHub에서 지난 버전 보기 | 저장소의 커밋 목록에서 커밋을 눌러 바뀐 줄 보기 |

`/rewind`는 빠르지만 한계가 있습니다. Claude가 파일 편집 도구로 고친 파일만 기억하므로, 명령으로 옮기거나 이름을 바꾸거나 지운 파일은 돌아오지 않습니다. 대화가 다르면 쓸 수 없고 다른 PC에도 없습니다. 그래서 공식 문서도 버전 관리를 대신하지 않는다고 적어 둡니다([Checkpointing](https://code.claude.com/docs/en/checkpointing#limitations)). 커밋이 진짜 안전망인 이유입니다. 데스크톱 앱에서 <Kbd keys="esc" />는 되돌리기가 아니라 "멈춤"이라는 점도 기억하세요. 되돌리기 메뉴가 설명과 다르게 보이면 "방금 한 변경을 되돌려 줘"라고 말로 시키면 됩니다.

</DeepDive>

**① 대화 되돌리기.** 커밋하지 않을 변경을 하나 시킵니다.

<PromptCard title="망가뜨리기 1" text="README.md를 전부 영어로 바꿔 줘. 커밋은 하지 마." compact />

입력창에 `/rewind`를 입력하고, 이 요청을 고른 뒤 코드를 되돌리는 항목을 선택합니다. 메뉴가 보이지 않거나 다르게 생겼으면 "방금 README를 영어로 바꾼 것을 되돌려 줘"라고 말로 시킵니다. README가 한국어로 돌아왔는지 확인하세요.

**② 파일 하나만 커밋 상태로.** 이번에는 두 파일을 고치게 한 뒤 하나만 되돌립니다.

<PromptCard title="망가뜨리기 2" text="README.md의 쓰는 법을 10단계로 아주 길게 다시 쓰고, index.html의 제목 글자도 두 배로 키워 줘. 커밋은 하지 마." compact />
<PromptCard id="git-restore-file" compact />

README만 돌아오고 제목 크기는 그대로인지 봅니다. 확인했으면 "아직 커밋하지 않은 변경을 모두 버려 줘"로 정리합니다.

**③ GitHub에서 지난 버전 보기.** "푸시해 줘"로 올린 뒤 GitHub 저장소를 브라우저로 엽니다.

| 볼 것 | 위치 |
| --- | --- |
| 커밋 목록 | 파일 목록 위의 시계 아이콘과 "commits" |
| 그 커밋에서 바뀐 줄 | 커밋 하나를 누르면 초록(추가)·빨강(삭제)으로 표시 |
| 그 시점의 파일 전체 | 커밋 화면의 **Browse files** |
| 비공개 여부 | 저장소 이름 옆의 **Private** |

</Trouble>

## 3단계 함께 고치는 법

이 단계를 마치면 브랜치와 풀 리퀘스트가 왜 있는지 알고, 혼자서도 그 흐름을 한 바퀴 돌아 볼 수 있습니다.

<Analogy title="교과협의회에서 평가계획서를 함께 고친다면">
  공유 폴더의 평가계획서를 두 선생님이 동시에 열어 고치면, 나중에 저장한 사람이 앞사람의 수정을 덮어씁니다. 그래서 "최종_김가온", "최종_이나래 수정"이 생깁니다. GitHub에서는 각자 <b>수정안 사본(브랜치)</b>에서 고치고, <b>협의회 안건(풀 리퀘스트)</b>으로 올려 바뀐 줄을 함께 본 뒤, 합의된 것만 <b>확정본(main)</b>에 반영합니다. 덮어쓰기가 없고, 누가 언제 무엇을 왜 바꿨는지가 모두 남습니다.
</Analogy>

| 개념 | 뜻 | 협의회에 빗대면 |
| --- | --- | --- |
| <Term id="collaborator">협업자</Term> | 비공개 저장소에 초대받은 사람 | 같은 교과 선생님 |
| <Term id="clone">클론</Term> / <Term id="pull">풀</Term> | 저장소 내려받기 / 최신 변경 받아 오기 | 문서철 받기 / 최신본 받기 |
| <Term id="branch">브랜치</Term> | 확정본을 건드리지 않는 작업 사본 | 수정안 |
| <Term id="pull-request">풀 리퀘스트</Term> | 합쳐 달라는 요청과 검토 창구 | 안건 상정 |
| <Term id="code-review">리뷰</Term> → <Term id="merge">머지</Term> | 읽고 의견 → 확정본에 반영 | 검토 의견 → 확정 |
| <Term id="conflict">충돌</Term> | 같은 줄을 서로 다르게 고친 상태 | 같은 문단의 두 수정안 |

흐름은 늘 같습니다. **최신으로 맞추기(pull) → 브랜치 → 고치고 커밋 → 푸시하고 풀 리퀘스트 → 검토 → 머지.** 충돌은 사고가 아니라 알림입니다. 다른 곳을 고친 변경은 Git이 알아서 합치고, 같은 줄만 사람에게 묻습니다.

<DeepDive title="AI와 함께 고칠 때 누가 무엇을 하나">

| 일 | Claude Code에게 맡길 것 | 사람이 할 것 |
| --- | --- | --- |
| 수정안 만들기 | 브랜치 생성, 수정, 커밋, 풀 리퀘스트 작성 | 무엇을 바꿀지 정하기 |
| 1차 검토 | 바뀐 내용 요약, 빠진 점·개인정보·키 점검 | 의견을 골라 남기기 |
| 충돌 | 양쪽을 나란히 보여 주기, 고른 대로 정리 | 어느 쪽을 남길지 결정 |
| 확정 | | **합치기 버튼은 사람이 누른다** |

AI가 빠르게 많이 만들수록 "사람이 읽고 확정한다"는 단계가 더 중요해집니다. Vercel과 이어 두면 이 단계가 화면으로도 보입니다. 풀 리퀘스트를 올리면 Vercel이 그 수정안만 담은 <Term id="preview-deploy">미리보기 주소</Term>를 댓글로 남기고, main에 합쳐지는 순간 실제 주소가 바뀝니다([Vercel 문서](https://vercel.com/docs/git/vercel-for-github)). 다만 무료 요금제에서는 계정 주인이 쓴 커밋만 배포되므로([Vercel 문서](https://vercel.com/docs/git)), 동료의 커밋은 따로 확인이 필요합니다.

</DeepDive>

## 5단계 Vercel 대시보드와 4회차 준비

이 단계를 마치면 배포가 잘못됐을 때 어디를 볼지 알고, 4회차에 쓸 계정이 준비됩니다.

<DeepDive title="Vercel 대시보드, 여기만 알면 된다">

| 메뉴 | 쓰는 때 |
| --- | --- |
| **Deployments** | 배포 기록. 푸시할 때마다 한 줄씩 생깁니다 |
| 배포 하나 → **Build Logs** | 빌드가 실패한 이유. 빨간 줄을 복사해 Claude Code에 |
| **Instant Rollback** | 방금 배포가 잘못됐을 때 이전 배포로 즉시 되돌리기. 무료 요금제는 바로 이전 배포로만 가능합니다 |
| **Settings → Domains** | 주소를 기억하기 쉽게 바꾸기 |
| **Settings → Deployment Protection** | 로그인한 사람만 보게 제한(Vercel Authentication) |
| **Settings → Environment Variables** | 4회차에서 키를 넣는 곳 |

Instant Rollback을 쓰면 Vercel은 그 뒤의 푸시를 실제 주소에 자동으로 올리지 않습니다. 고친 뒤에는 프로젝트 첫 화면의 <b>Manage</b>에서 최신 배포를 골라 다시 올려야 평소처럼 돌아갑니다([Vercel 문서](https://vercel.com/docs/instant-rollback)). 그래서 평소에는 Git으로 되돌려 다시 푸시하는 쪽이 단순합니다. 메뉴 이름이 다르면 [Vercel 공식 문서](https://vercel.com/docs)를 확인하세요.

</DeepDive>

<Lab session={3.5} title="미션 5 · 대시보드 둘러보고 4회차 준비" level="필수" minutes={20}>
<Step id="m3-14" title="배포 기록과 빌드 로그 찾기">

[Vercel 대시보드](https://vercel.com/dashboard)에서 보드 프로젝트를 열고 **Deployments**에서 미션 3의 머지로 생긴 배포를 찾습니다. 눌러서 **Build Logs**를 펼쳐 보세요. 풀 리퀘스트 때 생긴 미리보기 배포도 목록에 있습니다.

</Step>
<Step id="m3-15" title="(선택) 이전 배포로 되돌렸다가 돌아오기">

프로젝트 첫 화면의 **Instant Rollback**으로 바로 이전 배포로 되돌리고, 배포 주소가 예전 모습인지 확인합니다. 확인했으면 **Manage**에서 최신 배포를 골라 원래대로 돌려놓으세요. 돌려놓지 않으면 다음 푸시가 반영되지 않습니다.

</Step>

</Step>
